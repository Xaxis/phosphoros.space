# Model

Every number Phosphoros publishes, computed from `data/` by `calc/`, with its formula, inputs and the physics checks.

<!-- covers: cli:calc, export:@phosphoros/calc, export:@phosphoros/calc/*, export:@phosphoros/calc/load -->

## Sub-features

- all: `pnpm calc` prints every derived number, then every physics check.
- only: `--only ID` prints one number with value, SI value, formula, inputs and where it is defined.
- set: `--set ID=VALUE` (repeatable, dates as YYYY-MM-DD) reruns the model with an input changed.
- json: `--json` prints inputs, derived numbers and checks as JSON.
- claims: `--claims` compares every number in the version 2 brief (`data/claims.yaml`) with the model; exits 1 only on an unexplained difference.
- package: `@phosphoros/calc` (browser-safe: `compute`, formatting, registry, time), `@phosphoros/calc/load` (Node only: reads `data/`), `@phosphoros/calc/content` and `@phosphoros/calc/template`.

## How to reach it

- `pnpm calc`, `pnpm calc --only veil-distance`, `pnpm calc --set foundry-doubling-days=70`, `pnpm calc --json`, `pnpm check:claims`.
- Imported by `web/lib/model.ts`, `web/components/Explorer.tsx` (in the browser), `tools/*.ts` and `figures/src/*`.

## How to check it

Static: `pnpm test` (calc/test/model.test.ts), `cd calc && pnpm typecheck`.

Runtime:

```sh
pnpm calc --only veil-distance; echo "exit $?"
pnpm calc --set foundry-doubling-days=70 | grep -E "Earth-like|earth-like-by-deadline"
pnpm calc --claims | tail -3; echo "exit $?"
pnpm calc | grep -E "heat books|frozen through|^checks"
```

Proves it when: `--only` prints "Veil station, sunward of Venus" with a value in km and its inputs, exit 0; the 70-day variant shows the `earth-like-by-deadline` check failing and a 2037 date; `--claims` ends with a summary of match, corrected and explained counts and exits 0; the grep shows "PASS  The simulation's heat books balance" and "PASS  The seas are frozen through before the last caps are sealed", with `checks-failing` equal to the failures listed in SKILL.md (6).

## Gotchas

- `load.ts` finds the repository by walking up to `pnpm-workspace.yaml`; run from inside the checkout.
- The first run in a process solves the Ice Train's launch schedule (about 200 ms, then cached in `ice.ts`). After that the ozone model (`calc/src/model/ozone.ts`) and the trajectory module (the plan's simulation plus the loss-heat variant) take most of a run, a few tens of ms each. It reads `calc/src/spectra.ts`, generated by `node tools/spectra.ts` from `data/spectra/`; `pnpm lint` fails if the table is stale. Its growth is converged at `STEPS` per day: halving them moves `ozone-shield-days` by about a day. `pnpm calc --only ozone-model-earth` should stay near `earth-ozone-column` (check `ozone-model-earth`).
- `compute()` may run the model more than once. When the Ceres factories (`ceres-ready`) finish after the Lattice's full power, launches wait for them; a later start finds the planets elsewhere, which changes the launch cost, the Railheads and the Crown, so `compute()` reruns with `Registry.solved["ceres-ready"]` until `ice-launch-start` meets `ceres-ready` (to `READY_TOLERANCE_DAYS`). A later start lets the factories finish sooner, so plain substitution rings; the loop takes secant steps on the gap. The plan takes one pass; a late Ceres variant takes a few. `pnpm calc --set ceres-doubling-days=55` shows it: `ice-launch-start` equals `ceres-ready`. The simulation's totals sum the whole run, not to the deadline, so `traj-heat-books` holds in late variants too.
- Module order matters because evaluation is eager: `helios` (the Lattice's size and mass) runs before `foundry`, because the Foundry's doubling count is the soonest finish for what it builds next (`foundry-target-mass`, the Lattice and the hardware for Venus), and `heliosSchedule` (build days, full power, supply) runs after it. the `foundry-size` check and the test "the Foundry stops at the soonest finish" confirm the rule.
- Ledger line links come from `sourceLines` in `calc/src/load.ts`: an id's literal `"id"` first, then the template that builds it in a loop (`traj-${k}`, `${id}-power`). A new loop-built id should use one of those forms so its link lands on the loop.
- Cooling waits for the hardware at Venus: `cooling-start`, defined in `foundryProducts`, is the later of the Foundry's full scale and `venus-hardware-ready` (built after the Lattice). The Exhaust's campaign averages divide by the cooling time, so they live in `exhaustAverages`, which runs after `foundryProducts`. `pnpm calc --only cooling-start` shows the hardware's date in the plan.
- Where each world is on each day: `placeOf(v, world, day)` in `places.ts` (Mercury, Venus and Earth from Standish's mean elements, Ceres from JPL's osculating ones), browser-safe and shared by the model and the home page's journey, and logged as `orbit-<world>-longitude` and `orbit-<world>-distance` series. `calc/test/model.test.ts` holds it to the sky (Earth at 180° at the 2027 March equinox, Venus near Earth at the October 2026 conjunction), and `web/test/journey.test.ts` holds the journey's placer to the logged series.
- The launches are booked on their real dates: `campaignSchedule` in `physics.ts` places Ceres and Venus by their measured elements on each launch day and assigns every day's Bricks to the cheapest transfer with an arrival slot free (Hungarian assignment). `iceArrivals(v)` in `ice.ts` turns the booked arrivals into each day's heat in the simulation. The Bricks' heat outruns the lit chimneys, so the air warms back (`traj-rewarm`) and the Clear Rain begins for good later (`traj-rerain`); the `forges-on-seas` check holds the Forges to that date.
- The test "every Explorer slider runs end to end" sweeps every ranged input across its range (about 10 s). A new input range, or a new way for the model to stop, must either run there or throw one of the designed messages the test lists.
- An input that nothing reads fails the test "every input is read". Link it from a doc or a spec row, or remove it.
- Changing a published number needs a `data/corrections.yaml` entry, not a silent edit.
